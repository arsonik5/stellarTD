# Mistakes

Bugs and dead ends hit during development, and how they were actually fixed. Append a new entry whenever something non-obvious breaks and gets fixed — the point is to not pay for the same lesson twice, especially anything involving the `godot_voxel` GDExtension, whose docs are sparse/version-inconsistent.

## 2026-09-03 — `Building.input_capacity`/`output_capacity` were wrongly enforced as a hard storage cap

`can_accept_input`/`can_add_output` gated deposits on `get_input_count() + amount <= input_capacity` (default 15) in addition to the real storage ceiling `inventory_capacity`. This meant Chest (`inventory_capacity=300`) silently refused deposits past 15 items even though it had 285 slots of room left — the intent was always for `input_capacity`/`output_capacity` to read as a throughput *rate* (a later concept, e.g. for a power/logistics system), never a storage wall.

**Fix**: `can_accept_input`/`can_add_output` now check only `get_total_count() + amount <= inventory_capacity`. `input_capacity`/`output_capacity` stay as exported fields (still shown in the building UI title) but no longer gate anything.

**Missed on the first pass**: `can_accept_input` returning true isn't enough on its own — `building_ui.gd`'s `_place_on_building`/`_quick_transfer_player` each pre-clamp the amount to a locally-computed `room` *before* ever calling `can_accept_input`, and that `room` was still `input_capacity - get_input_count()` (the same 15-item wall, just recomputed one layer up). Fixing only `can_accept_input` still left manual GUI drag/shift-click transfers capped at 15 even though `can_accept_input` itself would have allowed more — the cap moved, it didn't disappear. Both `room` calculations needed the same swap to `inventory_capacity - get_total_count()`. Grep every call site of a changed gating function for a duplicated pre-check, not just the function itself, before considering a "remove this cap" fix complete.

## 2026-09-04 — GDScript lambda closures capture outer locals by value, not reference

Wrote a driven headless test for `EnemyScoutShip` using the obvious pattern: `var reported_value = null; scout.left_system.connect(func(r): reported_value = r)`, then polled `reported_value` after awaiting physics frames. It never updated — stayed `null`/`false` forever even though the signal genuinely fired (confirmed separately: `ThreatDirector`'s own bound-method handler on the same signal updated its own object field correctly). A `func() -> ...` lambda in GDScript captures enclosing local variables by value at creation time; assigning to the captured name from inside the lambda only mutates the lambda's private copy, it never writes back to the outer scope's variable.

**Fix**: capture a mutable container instead of a plain var — `var box := [null]`, lambda does `box[0] = r`, caller reads `box[0]`. The `Array` reference itself is what's captured by value, but its contents are shared, so mutating an element is visible outside. Relevant to any future driven test that waits on a signal via an inline lambda + polling loop, not specific to this system.

## 2026-09-04 — Driving a `CharacterBody3D` in a headless test via manual `_physics_process(dt)` calls doesn't move it

Tried to fast-forward `EnemyScoutShip`'s flight in a driven test by calling `scout._physics_process(0.05)` directly in a tight loop instead of waiting on real engine frames. The state machine barely advanced no matter how many iterations ran. `move_and_slide()` ignores whatever `delta` your own function received and always reads the engine's actual current physics-frame delta internally — calling it outside of a real physics tick does effectively nothing, regardless of what you pass your own `_physics_process`.

**Fix**: drive real time with `await get_tree().physics_frame` in a loop (capped at N iterations) instead of manually invoking `_physics_process`. Once switched, the same scout reached its scan point, scanned, and fled within 3 real physics ticks. Anything moved via `move_and_slide` needs real frames in a driven test, not a hand-rolled delta loop — a narrower case of the existing "instant teleport can outrun collision streaming" lesson elsewhere in this file.

## 2026-09-03 — Raw item ids in slot button text stretch `GridContainer` columns unevenly

`building_ui.gd`'s inventory grid rendered `slot.item_id` (e.g. `"refined_copper_ingot"`) directly instead of the item's `display_name`. A `Button`'s `custom_minimum_size` is only a floor — if unclipped text needs more horizontal space than that, the button (and therefore its whole `GridContainer` column) grows to fit it, so columns holding long-id items ended up visibly wider than columns holding short ones (`"ore_a"`). `inventory_ui.gd`'s player-grid already used `display_name` and never showed the bug.

**Fix**: switched `building_ui.gd`'s slot text to `Inventory.get_item_def(item_id).display_name` (added a `_display_name()` helper), and set `clip_text = true` on every grid/hand slot `Button` as a hard backstop so no future long name can force a column wider than its `custom_minimum_size` again.

## 2026-09-03 — Headless `--quit-after N` counts render frames, not real seconds — Timer-based logic needs wall-clock-driven test assertions, not frame-count milestones

Wrote a driven wrapper-scene test (per the pattern below) to verify Building's new timer-based crafting (`process_recipe`/auto-craft), gating assertions on frame numbers like "at frame 100, check the Smelter's output" assuming ~60fps. Every assertion failed — not because the code was broken, but because headless mode runs `_process` uncapped (no vsync/fps limit), so it can burn through hundreds of frames in well under a second of real time. A `Timer` with `process_callback = TIMER_PROCESS_IDLE` counts down using each frame's real elapsed `delta`, so its real completion time is close to its `wait_time` in actual wall-clock seconds regardless of frame count/rate — "frame N" is not a reliable proxy for "N/60 seconds have passed" under headless.

**Fix**: gate test assertions on `Time.get_ticks_msec() - start_ms` (wall-clock elapsed) instead of a frame counter, with generous margins for `process_time`-driven logic, and pass a very large `--quit-after` value as a backstop while the test's own `get_tree().quit()` (called once its own elapsed-time budget is used up) is what actually ends the run.

## 2026-09-03 — Stale headless Godot process locks the GDExtension DLL

Running the headless smoke-test command back-to-back sometimes fails with `Failed to open '...editor.x86_64.dll'` / `Can't open GDExtension dynamic library`. Cause: a previous headless run didn't actually exit despite `--quit`/`--quit-after`, and it's still holding `addons/zylann.voxel/bin/libvoxel.windows.editor.x86_64.dll` open.

**Fix**: check `Get-Process | Where-Object { $_.ProcessName -like '*Godot*' }` and stop any lingering instance before retrying. Don't assume a prior headless run has exited just because the command returned.

## 2026-09-03 — `TEXTURES_SINGLE_S4` silently produces blank texturing without an explicit `VoxelFormat`

`VoxelMesherTransvoxel.texturing_mode = TEXTURES_SINGLE_S4` needs the terrain's `CHANNEL_INDICES` to be 8-bit. The *default* format is 16-bit, which triggers only a warning (`Indices channel is set to 2 bits, but only 8 bits are required` — the "2" is the `Depth` enum ordinal for 32-bit, not literal bits, so the wording is misleading), and the mesher then emits all-zero per-vertex material data (verified directly: `CUSTOM1` array was `[0.0, 0.0, ...]` for every vertex even on a buffer with real varied `CHANNEL_INDICES` content).

**Fix**: build an explicit `VoxelFormat`, `set_channel_depth(VoxelBuffer.CHANNEL_INDICES, VoxelBuffer.DEPTH_8_BIT)`, and assign it to `terrain.format` before assigning the generator/mesher. See `scripts/world/world.gd`.

**Related trap**: `CHANNEL_WEIGHTS` does *not* accept `DEPTH_8_BIT` — calling `set_channel_depth(CHANNEL_WEIGHTS, DEPTH_8_BIT)` throws `Depth of 1-bits is not supported by channel 'weights'` and blocks `_ready()` outright. Only set the indices channel's depth; leave weights at its default.

## 2026-09-03 — Ore veins placed too deep/rare to find in a normal play session

First ore-vein pass used `ORE_VEIN_DEPTH_MIN/MAX = 2.0/14.0` (voxels below the surface) with noise thresholds `0.55`/`0.6`. Since the player only reaches 0-2 voxels deep with normal surface digging, this meant "no veins to mine" in practice even though the generator logic itself was correct.

**Fix**: moved the band to start at the surface (`0.5`) and lowered thresholds to `0.25`/`0.3`. Verified via a headless generator test before shipping: ~9% ore A / ~6% ore B of near-surface solid voxels. See `scripts/world/ore_generator.gd`.

## 2026-09-03 — Renaming a `class_name` script outside the editor leaves a stale global class cache

Renamed `scripts/data/ore_type.gd` (`class_name OreType`) to `scripts/data/item.gd` (`class_name Item`) via `rm`/`Write` instead of the editor's rename. Every script referencing `Item` as a type then failed with `Could not find type "Item" in the current scope` — Godot's `.godot/global_script_class_cache.cfg` still only knew about `OreType`.

**Fix**: run `--headless --path . --import --quit` once after any `class_name` rename/move done outside the editor, before booting the game. This forces a full rescan that rebuilds the global class cache.

## 2026-09-03 — Tab gets eaten by GUI focus-navigation once a Button has focus

Implemented Tab to toggle the inventory UI in `_unhandled_input`. Worked once — after the inventory opened and a slot `Button` got clicked (Buttons grab keyboard focus on click by default), pressing Tab again did nothing: player got stuck with the mouse released and no way back into the game. Root cause: Tab is bound to Godot's built-in `ui_focus_next` action; once any `Control` has focus, Tab is consumed by focus-navigation *before* it reaches `_unhandled_input`.

**Fix, two parts** (`scripts/player/player.gd`, `scripts/ui/inventory_ui.gd`):
1. Move the Tab/Escape menu-toggle handling into `_input()` instead of `_unhandled_input()` — `_input` fires before GUI consumption in Godot's dispatch order, so it can't be swallowed this way.
2. Set `focus_mode = Control.FOCUS_NONE` on every inventory slot `Button`. A click-to-carry slot grid never needs keyboard focus navigation, so there's no reason to let it participate at all.
Escape was also made a secondary "close inventory" input as a safety net in case Tab breaks again for some other reason.

## 2026-09-03 — Caching a `get_first_node_in_group()` lookup in `_ready()` is scene-order-dependent

`player.gd`'s `_ready()` cached `get_tree().get_first_node_in_group("inventory_ui")`. It silently returned `null` because `Player` appears *before* `InventoryUI` in `scenes/world.tscn`, and `InventoryUI` only joins that group via `add_to_group()` inside its own `_ready()` — which hadn't run yet when `Player._ready()` did the lookup. Symptom was confusing: the mouse-mode toggle (unrelated to the lookup) still worked, so Tab visibly "did something" while the actual UI never showed.

**Fix**: don't cache node references obtained via a *runtime* `add_to_group()` call inside another node's `_ready()` — look them up fresh at the point of use instead (cheap, since it's only on a Tab/Escape press, not a hot path). Note this does **not** apply to `_terrain`, which stays cached fine: `Terrain`'s group membership is declared statically in the `.tscn` (`groups=["voxel_terrain"]` on the node header), which is applied at node instantiation, not at `_ready()` time — so it has no such ordering hazard.

## 2026-09-03 — `-s custom_script.gd` doesn't have autoloads at compile time

Tried to write an isolated `SceneTree`-extending test script (per the pattern below) that referenced the `Inventory` autoload directly, or that instantiated a scene whose script (`processor.gd`, `player.gd`) references it. Both failed with `SCRIPT ERROR: Compile Error: Identifier not found: Inventory` — not a runtime null, a **compile-time** failure, because GDScript resolves autoload singleton names against the project's registered-singletons table, and that table isn't populated yet this early when Godot is running a custom main-loop script via `-s`. A normal full boot (no `-s`, just `--quit-after N` against the real `run/main_scene`) resolves `Inventory` everywhere without issue — this is purely a `-s`-mode limitation, not a real bug in any script that trips it.

**Fix, for a scripted integration test that needs autoloads**: don't use `-s`. Instead temporarily point `project.godot`'s `run/main_scene` at a throwaway wrapper scene (root node instancing the real main scene by the same name it already has, e.g. `[node name="World" instance=...]`, plus a sibling `Node` running the test logic in `_process()`), run a normal headless boot against it, then revert `run/main_scene` and delete the wrapper scene/script. Verified this way for the build-tool camera state machine (`player.gd`'s `_toggle_build_mode()`/tween/ghost/placement flow) — driving the real methods on the real `Player` node under a real boot caught what a passive `--quit-after` idle-frame boot never would, since that boot receives no input and never calls any of this code at all.

**Also confirmed while doing this**: `Input.mouse_mode` reads back `MOUSE_MODE_VISIBLE` (0) under `--headless` even right after `Player._ready()` explicitly sets `MOUSE_MODE_CAPTURED` — headless has no real `DisplayServer` to actually capture a cursor into, so the property write is accepted but not honored. Don't read this as a bug when it shows up in a headless test; it's not observable in the real windowed game.

## 2026-09-03 — Perspective camera + mouse-raycast placement scales non-uniformly across the screen

The build tool's top-down camera was first built as a *perspective* camera pitched at -75° (not straight down), with the ghost following a raycast through the mouse cursor (`camera.project_ray_origin/normal`). Playtest: the ghost tracked the cursor reasonably near screen center but shot far away from it near the edges — "mouse not scaling properly." Root cause is inherent to perspective + non-vertical angle, not a math error: perspective rays *diverge* from the camera and, at a shallow angle to the ground, a ray a few pixels further from center can travel a much longer distance before hitting the ground plane than one near center — the mapping from screen offset to world offset is nonlinear and gets worse the further off-center and the shallower the pitch.

**Fix**: switch the build camera to `camera.projection = Camera3D.PROJECTION_ORTHOGONAL` with the pitch at exactly `-90°` (straight down) instead of perspective at an angle. Orthographic rays are parallel (confirmed via a driven headless test: `project_ray_normal` returned the exact same `(0,-1,0)` at every sampled screen position, and world-space X per equal pixel step was bit-for-bit identical at two different sample points), so screen offset maps to world offset at one constant ratio everywhere — no blow-up near edges. `Camera3D.size` (not camera height) becomes the zoom control in this mode; height above the focus point can just be a fixed constant high enough to clear terrain, since orthographic apparent size doesn't depend on distance. Switched projection back to `PROJECTION_PERSPECTIVE` only once fully settled back into the FPS pose (in the exit-tween's completion callback), so the switch itself is imperceptible — never mid-animation, which would pop.

**General lesson**: any raycast-from-cursor placement/selection scheme needs either an orthographic camera or a raycast against a *plane at a known height* (not the literal ground mesh) to get a screen-linear, predictable feel; a perspective camera at a shallow-ish angle will always feel "off" the further the cursor gets from center, no matter how correct the raycast math is.

## 2026-09-03 — `rotate_y()` rotates around the *parent's* Y axis, not the node's own local Y — breaks on a sphere

Converting the player controller to radial planet gravity, mouse-look yaw kept using `rotate_y(-event.relative.x * MOUSE_SENSITIVITY)` (inherited from the flat-world version). `Node3D.rotate_y` pre-multiplies the rotation onto the transform (`Basis(axis, angle) * basis`), i.e. it rotates around the *parent's* Y axis — fine when parent space has no rotation and the character's own up always equals world Y, but on a sphere the character's local up is constantly realigned away from world Y as it walks, so yaw input started spinning the camera around the wrong axis away from the spawn "pole".

**Fix**: `rotate_object_local(Vector3.UP, angle)` instead — it post-multiplies (`basis * Basis(axis, angle)`), rotating around the node's own *current* local Y axis, which is exactly the just-realigned "up" direction every frame. See `scripts/player/player.gd`'s `_align_to_up()` (rebuilds the body's basis each physics frame so local Y tracks radial-away-from-planet-center, preserving current facing via `Basis.looking_at()`) and the mouse-motion handler in `_unhandled_input`.

## 2026-09-03 — Instant teleport across a voxel planet can outrun collision streaming; real gradual movement doesn't

While driven-testing the sphere conversion, teleporting the player 45 world-meters in one frame (pole to equator, to save test time vs. actually walking there) produced a player that fell straight through solid terrain and settled ~17m *inside* the planet instead of on its surface — despite the exact same fall height/gravity setup working correctly at the spawn pole. Re-ran the same check with the player actually walking there via held WASD input instead (the real gameplay path) over ~13 simulated seconds, sampling `distance_to(planet_center)`/`up_direction` alignment/`is_on_floor()` every simulated second along the whole pole-to-near-opposite-pole arc — stayed glued to the surface (39.6–40.5m vs the nominal 40m radius) the entire way, never tunneled. Root cause understood as VoxelTerrain's background block generation/meshing not having caught up yet at the teleported-to location (confirmed by a lingering "Waiting for all tasks to be picked" warning at quit), which a real player walking there continuously never outruns since collision for the whole small planet is already within `VoxelViewer.view_distance` from frame one.

**Lesson**: don't use instant large-distance teleports to fast-forward a physics/collision test on streamed voxel terrain — the streaming lag itself becomes a false failure. Drive real input (`Input.parse_input_event` with a physical-keycode `InputEventKey`, held across ticks) over enough simulated time instead if the actual mechanic under test is "can the player get there by walking/falling normally."

## 2026-09-03 — Build camera's "perspective for the whole session" regressed a previously-fixed cursor-drift bug (only visible off-axis, not full-edges)

The 2026-09-03 entry above ("Perspective camera + mouse-raycast placement scales non-uniformly across the screen") already diagnosed and fixed this exact class of bug once, by switching the whole build-camera session to orthographic at a locked -90° pitch. At some point since, the build tool grew an adjustable-pitch orbit camera (`_build_camera_pitch`, RMB-drag, 15°-90° range, default 35°) that stayed on `PROJECTION_PERSPECTIVE` for the entire interactive session, not just the flight — silently reintroducing the same underlying bug, just reframed: since only *pitch* is tilted now (yaw rotation doesn't tilt the view relative to the ground plane), the horizontal screen axis stayed perfectly uniform and only the vertical axis was distorted, which is why it went unnoticed as "the same bug" for a while. Caught during the sphere-conversion pass when a peer session re-verified the build tool and quantified it: sampling `_screen_to_build_plane` at 5 equally-pixel-spaced points, world-space step size at pitch -55° went 70.0 → 13.9 → 6.0 → 3.3 (top to bottom) — a >20x sensitivity swing — while the horizontal axis stayed ~10.53/step everywhere.

**Why orthographic fixes it at *any* pitch, not just -90°**: for a perspective camera, ray *direction* varies per screen pixel (rays diverge from one origin), so intersecting with a plane the view isn't perpendicular to makes screen-offset → world-offset a genuinely non-uniform projective mapping. For an orthographic camera, ray *direction* is constant across the whole screen (only ray origin varies, affinely in screen coordinates) — so the same plane intersection reduces to an affine transform of screen coordinates, uniform everywhere, at any pitch. This is why the earlier fix's "-90° pitch" was never actually the load-bearing part; only the projection mode was.

**Fix**: keep `PROJECTION_PERSPECTIVE` only for the enter/exit flight tween (cosmetic, no world input is processed until `_build_view_ready` anyway), switch to `PROJECTION_ORTHOGONAL` once the flight finishes (`camera.size = _build_zoom` takes over as the zoom control, since orthographic apparent size doesn't depend on camera distance), switch back to perspective only once the *exit* tween completes — same "never mid-animation, which would pop" timing as the original fix. Verified via a driven headless test reproducing the peer's exact methodology (5-point pixel sampling at the default 35° pitch): both axes came back with a uniform-delta ratio of 1.000 post-fix. See `scripts/player/player.gd`'s `_enter_build_mode()`/`_update_build_camera()`.

**Lesson**: a documented fix for "screen-to-world mapping is non-uniform" needs to be re-verified (not assumed to still hold) whenever the feature it lives in grows new degrees of freedom — here, "pitch became adjustable" quietly broke an invariant ("camera always looks perpendicular to the ground plane") that the original fix's *effect* depended on, even though the fix's own code (`PROJECTION_ORTHOGONAL`) hadn't been touched — it had just been reverted back to perspective by a later, unrelated-seeming change.

## 2026-09-03 — Mining wouldn't dig more than 1-2 voxels and felt very slow: `VoxelTool.do_sphere()`'s radius is LOCAL (voxel-grid) space, not world space

Playtest report: holding the mining tool dug barely a dent and stopped making visible progress after 1-2 voxels. Root cause: `world.gd` sets `terrain.scale = VOXEL_SCALE` (0.4, so 1 local unit = 0.4 world meters) for finer voxel detail. `player.gd`'s `_dig()`/`_build()` pass `DIG_RADIUS`/`BUILD_RADIUS` (0.7/1.0, written assuming world-meter size) straight into `tool.do_sphere(center, radius)` — but unlike `VoxelTool.raycast()` (confirmed world-space, converts internally), `do_sphere()`'s `center`/`radius` are in the terrain's **local voxel-grid space**, not world space. This was previously misdocumented in `whatworks.md` and in a `world.gd` comment as "do_sphere is world-space-safe" — wrong, and specifically wrong in the direction that shrinks the dig sphere (2.5x smaller than intended: 0.7 local units = 0.28 world meters instead of the intended 0.7m).

Confirmed via two isolated headless `-s` tests against a throwaway flat `VoxelGeneratorScript` + scaled `VoxelTerrain` (not the real game scene): (1) a `do_sphere()` REMOVE call with a world-space center only ever flipped the SDF at the LOCAL coordinates numerically equal to the input, never the world-equivalent local position — proving `do_sphere()` is local-space, while a matching test proved `raycast()` genuinely is world-space. (2) Simulating `player.gd`'s exact per-tick dig loop (raycast → do_sphere at `hit.position`, `DIG_RADIUS` un-converted) against a flat surface: `hit.position` stayed frozen at the same voxel across 6 simulated dig ticks — reproducing "won't dig more than 1-2 voxels" exactly. Re-running with the radius divided by the terrain's scale factor made `hit.position` progress deeper every tick instead.

**Fix**: added `_local_radius(world_radius)` to `player.gd` (divides by `_terrain.scale.x`) and wrapped every `do_sphere()` radius argument (`DIG_RADIUS`, `DIG_FRAGMENT_THRESHOLD`, `BUILD_RADIUS`) with it. Corrected the misleading comments in `world.gd` and `whatworks.md`.

**Lesson**: when a terrain node has non-1.0 `scale`, don't assume every `VoxelTool` method shares one coordinate-space convention — `raycast()` and `do_sphere()` disagree (world vs. local respectively) on the exact same tool instance. Verify each method independently with an isolated test rather than extrapolating from one already-confirmed method to another.

## 2026-09-03 — VoxelTerrain background generation can lag a specific far region for tens of simulated seconds under concurrent system load, even with no teleporting involved

Extended the earlier teleport-vs-real-walking lesson (above): while driven-testing the new Foundation system, a `_terrain_supports()` check at the exact antipodal point from spawn (`(0,-40.375,0)`, straight-line ~93m from spawn, well inside the 256m world-space view distance) kept returning "no terrain found" even after waiting 900 *simulated* physics ticks (15s) and then 1500 ticks (25s) with the player never moving at all - while four other equally-far points (pole, two equator directions, an oblique direction) all resolved correctly within the first 900-tick wait. The failure was **isolated to placement validity** (`_terrain_supports` found no raycast hit) - the actual thing under test, ghost/foundation orientation (`up_dot`), was exactly `1.0000` there same as everywhere else, so this was a test-environment artifact, not a bug in the placement math.

Root cause understood as CPU contention: this session and at least two peer Claude sessions were running their own Godot processes concurrently at the time (`ListAgents` showed 3+ active peers, one mid-turret-feature headless testing). VoxelTerrain's background generation runs on worker threads that need real CPU time, not just simulated ticks - under multi-process contention, *simulated* wall-clock elapsing doesn't guarantee proportional *real* background-thread progress, and whatever internal order VoxelTerrain processes its generation queue in apparently made this one region the last to catch up.

**Fix**: didn't chase it further - dropped that one antipodal test point (the other 4 already give solid directional spread: pole, 2 independent equator axes, 1 oblique) rather than either (a) waiting arbitrarily longer with no guarantee it'd resolve before a headless run's own timeout, or (b) coordinating with every peer session to go quiet first, which doesn't scale as a routine testing practice.

**Lesson**: a driven test's *simulated*-time wait (`physics_frame` tick count) is not a reliable proxy for "enough real background-thread work has happened" when other processes are competing for the same CPU - this is a step further than the already-documented "headless runs frames uncapped" lesson, since even a very generous simulated-time budget can't guarantee real worker-thread throughput under contention. When a test's core claim (here: orientation math) is separable from an environment-dependent side effect (here: whether a specific far block has finished generating), assert on the separable claim and don't over-fit the test to require every incidental condition to hold everywhere.

## 2026-09-03 — Passing a freed `Object` into a statically-typed GDScript parameter throws at the call boundary, before the callee's own `is_instance_valid()` guard ever runs

Building the first Turret (targeting logic: cache `_target: Node3D`, re-validate each `_physics_process` tick), `_is_target_valid(target: Node3D)` had `is_instance_valid(target)` as its very first line - looked like a correct guard. Once a target actually died (`queue_free()`'d by `EnemyDummy.take_damage()`), every subsequent physics frame threw `SCRIPT ERROR: Invalid type in function '_is_target_valid'... The Object-derived class of argument 1 (previously freed) is not a subclass of the expected argument class` - spammed once per physics tick, forever, since `_target` was never being reassigned. Caught immediately by a driven headless test (see `whatworks.md`'s Turret entry) rather than in a live playtest.

Root cause: GDScript validates a statically-typed parameter's runtime class **at the call site**, before the callee's function body executes at all. A freed `Object`'s class can't be resolved anymore, so binding it to a `: Node3D`-typed parameter fails right there - the `is_instance_valid()` check *inside* `_is_target_valid()` never got a chance to run, because the call to `_is_target_valid(_target)` itself was the thing erroring.

**Fix**: check `is_instance_valid(_target)` in the caller (`_physics_process`) and null out `_target` there *before* it's ever passed to anything with a typed `Node3D`/custom-class parameter; also dropped the type annotation on `_is_target_valid`'s own parameter (untyped, so a freed reference can be passed in safely and checked inside the function body as originally intended).

**Lesson**: a validity guard only protects a function body - it does nothing about the type-check GDScript performs while binding the argument to a statically-typed parameter in the first place. Once an `Object` reference might be freed, either check `is_instance_valid()` *before* it touches any typed parameter anywhere, or keep the parameter untyped for exactly the function whose job is to validate it.

## 2026-09-03 — A ternary between a literal array and `[]` infers as plain `Array`, not the declared typed array

`projectile.gd`'s per-tick impact raycast built its exclude list as `var exclude: Array[RID] = [_exclude_rid] if _exclude_rid.is_valid() else []`. Parsed fine, but threw at runtime on literally every physics tick once a real projectile flew: `Trying to assign an array of type "Array" to a variable of type "Array[RID]"`. GDScript's ternary expression doesn't unify the two branches' array types the way a plain array literal does - `[_exclude_rid]` and `[]` both evaluate to untyped `Array`, and assigning that whole ternary result to an `Array[RID]`-typed variable isn't the same as assigning an array literal directly (which *does* get typed correctly from the variable's declared type). Caught by a driven test that let real projectiles fly for enough ticks to hit this path, not by the initial parse/boot smoke test - a type-mismatch inside a ternary branch doesn't show up until that branch actually executes.

**Fix**: build it imperatively instead - declare `var exclude: Array[RID] = []`, then `if cond: exclude.append(x)`. Unambiguous from the start, no ternary-array-typing question to run into.

**Lesson**: a plain array literal assigned directly to a typed-array variable gets typed correctly by the declaration; the same literal used as one branch of a ternary does not carry that typing through. When building a typed array conditionally, prefer imperative `append()` over a ternary/conditional-expression literal.

## 2026-09-04 — A parse error in an autoload script doesn't fail loudly at the call site - every reference to it just silently becomes `Nil`

Generalizing `PlanetPhysics` from a single-planet singleton to a multi-body registry, `get_up()` had `var up := pos - body.global_position` where `body` was typed `Node` (the return type of `get_nearest_body()`) - `Node` doesn't have `global_position` (only `Node3D` does), so `body.global_position` is a Variant access and `:=` couldn't infer a type, a parse error in `planet_physics.gd` itself. The actual symptom at boot was completely different and far more confusing: `SCRIPT ERROR: Invalid call. Nonexistent function 'get_nearest_body' in base 'Nil'` at every single call site across `player.gd`/`world.gd`/`planet.gd` - because the autoload's own script failed to compile, Godot logs `Failed to instantiate an autoload, script '...gd' does not inherit from 'Node'` once near the very top of boot output (easy to miss in a long log) and then the singleton identifier `PlanetPhysics` just resolves to `null` everywhere for the rest of the run, with no further indication *why*. Same root issue hit three more times in the same file (`get_nearest_terrain`/`get_planet_center`/`get_air_density` all had the identical `Node`-typed-var `.property`/`.method()` access pattern) - only the first one actually broke the parse (GDScript stops reporting a script's compile errors after the first one it can't recover from), so fixing one revealed the next only on the following run.

**Fix**: cast to the concrete type first (`get_nearest_body(pos) as Planet`) before touching any property/method the base `Node` return type doesn't have, or extract to an explicitly-typed intermediate variable (`var body_pos: Vector3 = body.global_position`) - same pattern as every other Variant-inference fix tonight, just easy to miss on a 4th occurrence in one file after already fixing the first three of a *different* file's projectile/turret code.

**Lesson**: when an autoload singleton identifier ever resolves to `Nil`/throws "nonexistent function" at a call site that used to work, check that autoload's own script for a parse error *first*, however unrelated the actual error site looks - a broken autoload fails silently (no boot-blocking error dialog, no crash) and just makes every one of its call sites look broken instead of pointing at the real, single root cause.
