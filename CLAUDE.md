# CLAUDE.md

Guidance for Claude Code in this repo.

## Output: minimum tokens only

No preamble/postamble, no restating the task, no summarizing what you just did unless asked. No filler ("Great question!", "Certainly!", "I hope this helps"). Answer directly; skip headers/bullets for short answers. Code: no comments unless requested. Explanations only when asked or a non-obvious decision needs one line of why. Match reply length to question complexity — one-line question gets one-line answer. When uncertain between terse and complete, choose terse; user will ask to expand.

**This also applies mid-task, not just to final replies (explicit user direction 2026-09-04)**: don't narrate what you're about to do between tool calls, don't restate a plan back to the user before executing it, don't recap findings the user can see in the tool output themselves. Investigate and act; report only the decision and the result. Don't ask a clarifying question when a reasonable default exists and the cost of guessing wrong is low (making the call and stating the assumption briefly is cheaper than a round trip) — reserve questions for choices that are genuinely the user's to make (scope, taste, irreversible actions).

**Hard cap, reinforced (explicit user direction 2026-09-04, user felt output was still too chatty)**: treat every reply as expensive. Default output is a diff/result plus, at most, one line of context — not a paragraph. No "here's what I did and why" walkthroughs, no restating what the code already shows, no listing next steps unless asked "what's next." A multi-file change gets a file list, not a per-file description, unless a file's change is non-obvious enough to need one clause. If a response is trending past ~5 lines, cut it down before sending — length is a bug, not thoroughness. Full detail only when explicitly asked ("explain", "walk me through", "why").

## Architecture principles (standing, from explicit user direction 2026-09-03)

**Multi-planet future, no reload between them.** The game will eventually have many procedurally generated planets and moons, plus open space ("shooting in the void") between them, and the player crosses between all of it without a scene reload/restart. Don't design anything as if exactly one planet will ever exist.

**Confirmed design direction (user, 2026-09-04)**: one continuous open space, not discrete instances you "enter/leave" (explicitly not Astroneer/No Man's Sky-style) - technically streamed/LOD under the hood for performance/precision, but no visible seam or loading transition. What stops the player from going anywhere is mechanical/realistic (fuel, oxygen/atmosphere) not a physical wall or height limit. A ship exists for real interplanetary travel; on-foot jetpack flight comes later for short hops. Exactly one procedurally generated star system per save (not a hand-authored fixed set, not unbounded/infinite generation). Full persistence is required - dug terrain and built structures must survive leaving and returning, since the stated endgame goal is running bases on multiple planets simultaneously.

**Phase 1 - done 2026-09-04**: the physics/generation layer is now genuinely multi-body. `scripts/world/celestial_body.gd` (`CelestialBody` resource: radius/seed/noise/ore-rarity/atmosphere - what used to be hardcoded consts in `ore_generator.gd`) + `scripts/world/planet.gd`/`scenes/planet.tscn` (`Planet`: owns its own `VoxelTerrain`, builds the generator from its own body, registers with `PlanetPhysics`) + a generalized `scripts/planet_physics.gd` (`register_body`/`unregister_body`/`get_nearest_body`, every gravity/atmosphere/terrain query resolving through nearest-in-range rather than "the one planet," with `Planet.influence_radius()` giving each body a bounded well so far-apart bodies have a genuine zero-gravity/vacuum gap between them rather than gravity always snapping to whichever is merely less-far). Proven with two simultaneously-registered planets (different radius/seed/atmosphere, one vacuum) before touching any gameplay code - see whatworks.md for the full writeup and mistakes.md for a parse-error-in-an-autoload gotcha hit along the way.

**Still not built** (deliberately deferred, each is its own substantial task - don't attempt speculatively, confirm scope first): a real procedural star-system generator (tonight's two bodies are hand-placed, not generated); floating-origin/precision handling for genuinely large distances (not yet needed at hundreds of meters, matters once real inter-planet distances are decided); a ship/vehicle controller + oxygen/fuel mechanics for actually reaching the void; save/persistence (currently zero save system exists anywhere in this project - `PlanetPhysics` registration is purely in-memory/runtime).

**Build systems once, compose them everywhere.** Define a capability once (inventory, ammo handling, modifier slots, ...) and give entities that capability through configuration (export fields like a size/capacity), not by re-implementing a parallel version per entity type. This is *why* `Building` is a base class every production building composes rather than each reimplementing storage, and why `Turret extends Building` reuses that same inventory instead of rolling its own ammo box. When adding a new entity that needs an existing capability, extend/compose the existing system - don't write a second one that looks similar but drifts (different edge cases, different bugs, inconsistent UI/feel). If two similar-looking systems already exist with genuinely different requirements (e.g. `PipeNetwork`'s exact-cell dictionary lookup for axis-aligned buildings vs. `FoundationNetwork`'s linear nearest-neighbor scan for arbitrarily-oriented foundations), that's fine *only* if the difference is real and load-bearing - say so explicitly in a comment, don't let it happen by accident.

Periodically sanity-check new work against both of these rather than assuming - see mistakes.md/whatworks.md for a live design/architecture log.

**Resolved 2026-09-03, same session this rule was written**: audited the codebase against it immediately and found a real violation - three independent hand-written "click to carry/place/merge/swap an item between slots" implementations (`inventory_ui.gd`, and two more inside `building_ui.gd`) had already drifted from each other. Consolidated into `scripts/ui/slot_carry.gd` (`SlotCarry`, the one implementation) driven through small duck-typed adapters per backing store (`inventory_slot_adapter.gd`, `building_inventory_adapter.gd`, `building_modifier_adapter.gd`). See whatworks.md for the design and PipeNetwork/FoundationNetwork remains the reference example of a *justified* divergence (real, load-bearing, documented) rather than an accidental one.

Verified via a driven WASD-walk headless test (pole to near-opposite-pole, `on_floor`/radius/up-alignment sampled every simulated second) — see whatworks.md. (Building world-Y-up gap fixed later the same session — see the foundation entry below.) Terrain shader (`scripts/world/voxel_debug_material.gdshader`) got two-octave hash-noise albedo/roughness variation plus a planet-latitude tint so materials don't read as flat-color plastic. Build-camera cursor mapping was also fixed this session: it now stays `PROJECTION_PERSPECTIVE` only for the enter/exit flight tween and switches to `PROJECTION_ORTHOGONAL` for the whole interactive placement session (a perspective ray intersected with a plane it isn't perpendicular to is non-uniform at any pitch other than -90°; orthographic rays are direction-constant across the screen, so the same intersection is affine/uniform at any pitch) — see mistakes.md.

Swapping the `atmosphere` export field to a different `.tres` is the entire "different planet" story — no shader/scene changes needed. `VoxelViewer.view_distance` doubled 320→640 (player.tscn). Verified headless that the shader-param/light/fog/view-distance plumbing all lands correctly; actual visual result needs the user's playtest (no GPU device under `--headless`).

**Metal Foundation / local-grid system (2026-09-03)**: `scripts/world/foundation.gd` (`class_name Foundation`, `SIZE=2.0` flat plate, center-anchored origin) + `scripts/foundation_network.gd` (new autoload, flat `Array` + linear nearest-neighbor scan — deliberately not a `Vector3i`-keyed dictionary like `PipeNetwork`, since foundations aren't axis-aligned). `player.gd`'s `_resolve_build_placement()` is the single source of truth for both the live ghost and the actual commit: a Foundation snaps to an existing neighbor's edge (copying its *exact* basis, not recomputing its own — this is what keeps a whole connected cluster flat/square to itself regardless of sphere curvature) or free-places tangent to raw terrain if none nearby; any other building mounts flush on a nearby foundation's top face (inheriting its orientation, R-key rotation still free on top) or free-places tangent directly on raw terrain as the explicit fallback. Ghost orientation is now recomputed from the cursor's *actual current position* every frame (not the build-session's entry-point snapshot used for the camera), fixing a milder version of the sphere-conversion's "sideways" bug that would've resurfaced once panning far from the entry point. Verified via a driven test: orientation exactly matches local radial direction at 4 well-spread points (pole, 2 equator axes, oblique — dot product 1.0000 every time), snapped foundations match their neighbor's basis exactly at exactly one tile-width apart, mounted buildings sit flush, and a full end-to-end placement through the real build UI/inventory/PipeNetwork pipeline works. See whatworks.md/mistakes.md for the design writeup and a VoxelTerrain background-generation timing gotcha hit during testing (unrelated to the placement logic itself). Known gap, not done: the pipe/merger/splitter conveyor system's own cardinal-direction math still assumes world-Y rotation, same underlying issue buildings just got fixed for — see gamebrief.md.

**Slice 2 started — Turret buildings (2026-09-03)**: `scripts/world/turret.gd` (`class_name Turret extends Building`), two scenes (`scenes/turret_gun.tscn` — fast, single-target, 14m range; `scenes/turret_cannon.tscn` — slow, splash, 20m range). Ammo is a plain `Building` inventory with `can_accept_input`/`can_add_output` overridden (no Recipe involved), so the existing `building_ui.gd` works as an ammo box. Targeting is group+duck-typed (`get_nodes_in_group("enemy")` + `has_method("take_damage")`), not a typed `Enemy` class — `scripts/world/enemy_dummy.gd` (`EnemyDummy`, health + `take_damage` + `"enemy"` group, no AI/movement) is a minimal test-target scaffold standing in for the real Slice-2 wave/AI system, which is still unbuilt. Head aiming reads its own `global_transform.basis.y` (not `Vector3.UP`) so it stays correct under the foundation system's surface-tangent orientation with no extra work. Not done: real enemy AI/movement/spawning, wave pressure scaling, power grid — still Slice 2 follow-up work, `EnemyDummy` is not that system.

**Volumetric ballistics (2026-09-03, explicit user request, replaces the turret's original hitscan)**: `scripts/world/projectile.gd` is a real simulated round — hand-integrated semi-implicit Euler physics each tick (gravity from the new `scripts/planet_physics.gd` autoload, shared with player.gd which was migrated onto it too so gravity/planet-center have exactly one source of truth; quadratic aerodynamic drag from `PlanetPhysics.air_density`, itself set from the active `PlanetAtmosphere` resource — a thinner/thicker atmosphere changes bullet drag automatically) plus a per-tick swept `PhysicsRayQueryParameters3D` raycast (prev-position to new-position, not a point check, so a fast round can't tunnel through a thin target in one step). `scripts/data/ammo_type.gd` (`class_name AmmoType`, plain `Resource`) owns the *complete* spec for one round — mass/muzzle_velocity/caliber/drag_coefficient AND damage/splash — deliberately not split across (turret, ammo), so different ammo types are what actually differentiates combat outcomes, not which turret fired them. `Turret.compatible_ammo: Array[AmmoType]` is an explicit allow-list (`iron_piercing_ammo` — both turrets; new `he_shell`, heavy/splash, cannon-only, crafted from `refined_material`+`gunpowder`) plus a runtime per-item `set_ammo_enabled()`/`is_ammo_enabled()` toggle so the player can lock out a compatible type without unloading it — both the allow-list and the toggle are surfaced in `building_ui.gd`'s new ammo row (only shown `if _building is Turret`). `turret.gd`'s `_compute_aim_point()` solves the classic no-drag ballistic-range quadratic for a firing-solution elevation angle (a deliberately simpler/separate model from the projectile's own drag-inclusive simulated flight — falls back to aiming flat if the target is beyond what the chosen ammo can ballistically reach at all). Modifier slots (`Building.modifier_slots`/`compatible_modifiers`, previously inert placeholder buttons) were made functionally real (`set_modifier_slot`, click-to-carry in `building_ui.gd`) but no modifier items/effects are designed yet — the mechanism exists, the content doesn't. Verified via a driven test: hand-recomputed expected velocity/position matches the real projectile after one integration step (sub-cm tolerance), trajectory visibly curves off a straight line under gravity, a turret auto-fires and actually damages an in-range target only once the projectile has flight time to arrive (not instantly), `set_ammo_enabled(false)` genuinely stops firing, a 2-ammo turret prefers its first-declared compatible/enabled/stocked type, and the building_ui ammo row round-trips real turret state. Caught and fixed a real runtime bug this way (a ternary between an array literal and `[]` silently produces an untyped `Array`, not the declared `Array[RID]` — see mistakes.md) that only threw once a real projectile flew far enough to hit that code path, invisible to a boot-only smoke test.
